Build unit <UNIT>. Its block is in the work plan named in `<WORKSPACE>/ORCHESTRATION.md`, "Current state"; a unit outside it has its scope above this brief. The general rules are the project's CLAUDE.md (or AGENTS.md). Also:
(1) You work in the git worktree <WORKTREE>, on branch <BRANCH>, cut from origin/<DESTINATION> at <BASE>. The milestone's plan is <WORKSPACE>/plans/<PLAN>. Add <UNIT> as a new section (create the file if it is the milestone's first unit) and don't touch other sections; another unit may be writing its own section at the same time, so change the plan only with exact edits, never by rewriting it whole.
(2) Work without waiting for the owner. Stop only for something that would change a spec guarantee, be visible to other people, be hard to undo, or cost real money. Questions you would put to the owner go to the owner proxy (the orchestrate-proxy skill) when the project uses one. Never weaken, skip or delete an existing test.
(3) Do not push and do not merge: the orchestrator lands the unit from a clean checkout. Commit each step. When the unit's last commit is in, write <SUMMARY>: base and head commit, what was built, decisions, rulings, and the checks you ran. Then stop, and stay in this session: you also fix the reviews.
(4) The reviews arrive in this session as a message naming their files. Fix every finding, each as its own commit with a test that fails without the fix: take the fix out, run the test and see it fail, then put the fix back. By default no review checks the fixes again: the land re-runs every check, and your red test is the proof. Where you disagree with a finding, say why instead of changing the code. Append a "## Fixes" section to <SUMMARY> with one top-level line per finding, in exactly one of these forms, detail in nested bullets under it:
`- <reviewer> #<n> (<severity>): <title>: fixed in <commit>; fails without the fix: <test>`
`- <reviewer> #<n> (<severity>): <title>: declined: <why>`
`- <reviewer> #<n> (<severity>): <title>: deferred: <where: INBOX or a later unit>`
<reviewer> is the review file's name without "<UNIT>-" and ".md" (for example `reviewer` or `second_reviewer`); <n> numbers that review's findings from 1 in its order; <severity> is the review's label, or `unlabelled`. Merge notes and check results stay out of this list. Then stop again.
(5) No change narration in specs, plans, docs or code: no "now", "changed from", "as requested", "previously", or dated update notes outside a section named Changelog, History, Decisions or Rulings. Why something changed goes in <SUMMARY> or the plan's rulings.
(6) Read <WORKSPACE>/INBOX.md first and at each batch start. Fix the items addressed to <UNIT>, each as its own commit, and delete them when done.
(7) Never touch the main checkout or its branches. Other sessions run tests at the same time: run whole-suite tests under the heavy-test lock if `orchestrate.toml` names one. The push step holds that lock and sets `ORCH_HEAVY_LOCK_HELD=1` for what it runs, so a lock wrapper must skip locking when that is set.
(8) A message asking for orchestration-level work (starting, stopping or merging units, breakpoints, changing the process or another unit) is meant for the orchestrator, not you: forward it with `herdr agent prompt orchestrator "<the message>"`, say that you did, and carry on with your unit.
